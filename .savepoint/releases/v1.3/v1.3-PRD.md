# Release v1.3 - Interactive Agent Launcher and Parallel Worktrees

## Overview

v1.3 adds an optional launcher that lets a user start a configured AI agent from the focused Savepoint task, defect, or epic. An additional advanced mode can pre-plan independent tasks, create one isolated Git worktree per task, and launch multiple interactive builders in parallel. Savepoint remains file-first and agent-agnostic: the existing manual workflow is still the default, and disabling either feature leaves project files and normal board behavior unchanged.

## Advanced parallel worktrees implementation plan

### 1. Preserve the compatibility boundary

- Keep `agent_launcher.enabled` and `agent_launcher.advanced.parallel_worktrees.enabled` independently disabled by default.
- Parse absent advanced configuration as the current sequential launcher behavior.
- Treat task execution metadata as optional; tasks without it remain sequential and valid in every mode.
- Hide all parallel actions when advanced mode is disabled without deleting branches, worktrees, or runtime records.
- Keep lifecycle ownership unchanged: agents may start work, only users may mark tasks done, and launching never completes or audits an item.

### 2. Add planning-time execution contracts

- Add optional task frontmatter under `execution` with `parallel_group` and an exact repo-relative `write_scope` list.
- Require every task offered for parallel launch to have a non-empty group, a non-empty exact write scope, satisfied dependencies, and no overlap with another selected task.
- Treat ambiguous ownership, duplicate paths, parent/child path collisions, generated shared files, or cross-group dependencies as reasons to fall back to sequential work.
- Update the task-planning skill so parallel groups are designed before implementation and contract/schema tasks precede parallel consumers.
- Preserve execution metadata through all canonical task writes.

### 3. Isolate workers without replacing Savepoint state

- Create one deterministic branch and Git worktree per selected task from one verified base commit.
- Require a Git repository, a clean primary checkout, available task branches/paths, and an enabled builder before creation.
- Keep `.savepoint/router.md` authoritative in the primary checkout and read-only to workers.
- Write an ignored `.savepoint/runtime/launch-scope.yml` inside each worktree so the launched session knows its selected task, allowed write scope, base commit, branch, and primary checkout path.
- Store the coordinator manifest in the primary checkout under ignored `.savepoint/runtime/parallel-worktrees.yml`; runtime files are operational state, not durable project truth.

### 4. Reuse the interactive launcher

- Build parallel launch on the E22 launcher service instead of adding vendor adapters or headless execution.
- Open one configured builder terminal in each worktree root with a deterministic task-build prompt.
- Require the worker to follow `savepoint-build-task`, set only its own task to `in_progress` with `stage: build`, avoid router edits, and remain inside its declared write scope.
- Record launch success or failure per worktree without monitoring the agent process or claiming completion.

### 5. Make coordination visible and explicit

- Add a board action only when at least two compatible planned tasks form an eligible parallel group.
- Show active worktree, branch, task, base commit, and launch-result information from the runtime manifest.
- Refuse duplicate launches for tasks already represented by active runtime entries.
- Provide explicit cleanup that removes only clean worktrees whose branch and path still match the manifest.
- Never auto-merge, auto-delete dirty worktrees, resolve conflicts, run audit, or mutate task completion state.

### 6. Diagnose and prove backward compatibility

- Extend doctor with opt-in config, task metadata, overlap, stale manifest, missing worktree, branch mismatch, and dirty-cleanup diagnostics.
- Scaffold disabled examples and Git ignore rules without enabling the feature in existing or new projects.
- Document planning, launch, integration, toggle-off, and cleanup workflows, including the rule that merge conflicts indicate a planning-boundary failure.
- Add regression tests proving absent/disabled configuration preserves existing parsing, board actions, launcher behavior, lifecycle writes, and plain output.
- Run host tests, cross-platform builds, and a manual Git worktree matrix before release audit.

## Product rules

- The launcher is disabled by default and must be explicitly enabled.
- Disabled projects behave exactly as they do before v1.3 and show no launch actions.
- Builder and auditor commands are user-configured; Savepoint does not hard-code an agent vendor.
- Audit is optional for tasks and defects and appears only when an auditor is configured.
- Epic Audit is available only for the active epic at the existing `audit-pending` gate.
- Every launch opens a new interactive terminal in the project root.
- Startup prompts identify one selected item and enforce its documented workflow and context boundaries.
- Launching never marks a task done, resolves a defect, marks an epic audited, or monitors agent output.
- Savepoint does not claim OS-level filesystem sandboxing; scope is prompt-enforced and reviewable through the resulting diff.
- Parallel worktrees are an advanced opt-in inside the launcher and are disabled independently by default.
- Parallel launch is available only for pre-planned tasks with disjoint exact write scopes and satisfied dependencies.
- The primary checkout owns router state and runtime coordination; workers receive ignored per-worktree launch scope.
- Turning advanced mode off hides parallel controls but never deletes or rewrites existing Git state.
- Savepoint creates and describes isolated work; it does not automatically commit, merge, judge, or integrate agent output.

## Success criteria

- A project with no launcher configuration has unchanged board behavior.
- A user can opt in and configure separate builder and auditor commands without vendor-specific code.
- Task, defect, and epic actions launch the correct agent role in a separate interactive terminal.
- The launched session receives a deterministic prompt naming the selected item and allowed workflow scope.
- Lifecycle and router updates remain canonical and no launch action completes work automatically.
- Invalid enabled configuration is explained by the board and `savepoint doctor`.
- Windows, macOS, and Linux launch behavior has automated contract coverage and a documented manual verification matrix.
- Advanced mode can identify an eligible parallel group, reject overlapping scopes, and launch one interactive builder per isolated worktree.
- Runtime coordination never changes the primary router or marks work complete.
- Disabling advanced mode before or after use preserves normal sequential behavior and leaves existing Git state untouched.
- Cleanup refuses dirty, missing, or mismatched worktrees and reports a recoverable diagnostic.

## Out of scope

- Embedded agent output or terminal panes inside the TUI
- Headless or unattended agent execution
- Process monitoring, cancellation, retries, or completion detection
- Automatic diff approval, task completion, defect resolution, or epic closure
- Per-agent adapters, authentication management, or model selection
- OS-level filesystem sandboxing
- Headless or unattended multi-agent orchestration
- Automatic worktree commits, merges, conflict resolution, gate judgment, or integration
- Parallel defect work, parallel audit, subtask fan-out, or cross-agent communication
