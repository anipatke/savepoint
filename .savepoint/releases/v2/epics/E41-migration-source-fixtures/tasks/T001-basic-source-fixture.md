# T001: Preserve a small project's migration source

## Problem

Existing legacy fixtures pin isolated assets but do not represent a complete active project with completed prerequisites. V1 parsing normalizes aliases and line endings; a future converter that uses only normalized models could lose evidence. Freeze source bytes and verify the current reader interpretation before conversion work begins.

## Outcome

A small V1 project has an immutable test input containing a completed Task, a dependent in-progress Task, user content, and legacy metadata. Tests show both the raw source and current dependency interpretation without modifying the fixture or live project.

## User Check

**Design notes:**

- The dependency reference in T002 is the legacy short-with-suffix form `T001-original` (not `T001`, not the full scoped ID). `ResolveDependency` reaches it through `isShortTaskRef`'s dash-prefix match, scoped by T002's explicit `Release`/`Epic` — the same fields `internal/board/board.go`'s `loadEpicTasks` sets after `ParseTaskFile`, which the tests mirror rather than relying on frontmatter/ID defaults.
- T002's frontmatter also carries an unknown top-level field (`legacy_note`) and an unknown nested field (`metadata.reviewer.name`); both round-trip through `Parser.ParseFrontmatter` into `map[string]any` and are silently absent from the typed `Task`, with no schema change required.
- T002-follow-up.md is frozen CRLF end-to-end (frontmatter and body); `internal/data/testdata/migration/.gitattributes` sets `v1-basic/** -text` so no platform or `core.autocrlf` setting can normalize it. Verified with `git check-attr text` and a post-`make test` byte/hash recheck.
- Characterization finding: the two checklist extractors in `parser.go` disagree on multiline authored items. `extractChecklistItems` (Implementation Plan → `Task.Checklist`) joins continuation lines into one string; `extractChecklistSection` (Acceptance Criteria → `Task.Acceptance`) has no continuation handling and silently drops every line after the first. `TestMigrationSourceBasicInterpretation` asserts both behaviors explicitly — this asymmetry is exactly the kind of evidence a future converter must consume from raw bytes, not from `Task.Acceptance` alone. No production code changed; existing behavior is preserved and now has named test coverage.
- `manifest.yml` hashes were computed once by hand with `sha256sum` over the frozen bytes and hand-copied into the file; `migration_source_test.go` only reads them back via `loadMigrationManifest` and compares recomputed hashes against that recorded value — never against a value derived from the same test run.
- `TestMigrationSourceBasicInventory` also walks the fixture's `project/` tree and diffs the file set against the manifest's recorded paths in both directions, so an untracked file or an unrecorded fixture addition fails loudly instead of going unnoticed.
- Failure-variant tests mutate copies only in `t.TempDir()`; the malformed-frontmatter and broken-dependency cases never touch `testdata/migration/`, and both tests finish with `assertFixtureBytesMatchManifest` re-verifying the frozen bytes.
- No `.savepoint/Health-Check.md` or `.savepoint/audit/` exist in this V1 fixture project; `manifest.yml`'s `absent_by_design` list names both and `TestMigrationSourceBasicInventory` asserts their absence, per TPL-03/DATA-03-style "absence is not a finding" framing.
